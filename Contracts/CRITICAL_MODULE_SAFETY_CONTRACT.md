## 📋 ماژول‌های حیاتی (Critical Modules)

### 🔴 **سطح 1 - CRITICAL (ممنوعیت مطلق)**
این ماژول‌ها **هسته اصلی سیستم** هستند:

1. **Authentication & Authorization**
   - `AspNetUsers`, `AspNetRoles`, `AspNetUserRoles`
   - `ApplicationUser`, `ApplicationUserConfig`
   - هرگونه تغییر در Identity System

2. **Patient Management**
   - `Patients` table
   - `Patient` entity & configuration
   - رابطه `ApplicationUser ↔ Patient`

3. **Financial & Payment**
   - `Payments`, `OnlinePayments`, `CashSessions`
   - `Factor`, `FactorItem`
   - هرگونه محاسبات مالی

4. **Database Relationships**
   - Foreign Keys
   - Entity Framework Configurations
   - `WithRequired`, `WithOptional`, `HasMany`, `HasOptional`
   - Migrations

### 🟡 **سطح 2 - HIGH RISK**
این ماژول‌ها **تأثیر مستقیم روی عملکرد** دارند:

- `Appointments`, `Receptions`
- `Doctor`, `DoctorSchedule`
- `InsuranceProvider`, `InsuranceTariff`
- `Services`, `ServiceTemplate`

### 🟢 **سطح 3 - MODERATE**
ماژول‌های عمومی:
- UI/UX Components
- Frontend JavaScript
- CSS Styles
- ViewModels (بدون تأثیر روی Database)

## ⚠️ الزامات قبل از تغییر (Pre-Change Requirements)

### قبل از هر تغییر روی ماژول‌های حیاتی، **الزامی است:**

#### 1️⃣ **درک منطق سیستم (System Logic Understanding)**
```
✅ الزامی:
   - چرا این کد اینطوری نوشته شده؟
   - چه سناریوهایی را پوشش می‌دهد؟
   - چه وابستگی‌هایی دارد؟
   - چه تأثیری روی سایر ماژول‌ها دارد؟
   
❌ ممنوع:
   - تغییر بدون درک کامل
   - حدس زدن منطق
   - فرض کردن بدون بررسی
```

#### 2️⃣ **سوال از کاربر (User Confirmation)**
```
✅ الزامی:
   قبل از هر تغییر حیاتی، این سوالات را بپرس:
   
   1. "مشکل دقیقاً چیست؟" (نمونه واقعی بخواه)
   2. "رفتار مورد انتظار چیست؟" (سناریوهای مختلف)
   3. "آیا این تغییر روی سایر ماژول‌ها تأثیر دارد؟"
   4. "آیا تست‌های خاصی لازم است؟"
   5. "آیا می‌توانم مثال یا لاگ خطا ببینم؟"
   
❌ ممنوع:
   - "فکر می‌کنم مشکل اینجاست..."
   - "احتماماً باید این را تغییر بدهم..."
   - "بگذار امتحان کنم..."
```

#### 3️⃣ **تحلیل تأثیرات (Impact Analysis)**
```
✅ الزامی:
   قبل از تغییر، بررسی کن:
   
   - کدام بخش‌ها از این کد استفاده می‌کنند؟ (grep/codebase_search)
   - چه تست‌هایی باید اجرا شوند؟
   - آیا Migration لازم است؟
   - آیا داده‌های موجود تحت تأثیر قرار می‌گیرند؟
   
❌ ممنوع:
   - تغییر بدون بررسی وابستگی‌ها
   - Migration بدون بررسی داده‌های موجود
   - فرض اینکه "فقط این بخش تأثیر می‌گیرد"
```

#### 4️⃣ **Incremental Changes (تغییرات تدریجی)**
```
✅ الزامی:
   - یک تغییر در هر زمان
   - تست بعد از هر تغییر
   - کامیت تدریجی
   - قابلیت Rollback
   
❌ ممنوع:
   - تغییرات گسترده همزمان
   - "بگذار همه را یکجا درست کنم"
   - تغییرات بدون امکان بازگشت
```

## 🚫 ممنوعیت‌های مطلق (Absolute Prohibitions)

### **هیچ‌وقت اینکارها را انجام نده:**

1. ❌ **تغییر Entity Framework Relationships بدون درک کامل**
   ```csharp
   // ممنوع بدون بررسی:
   .WithRequired() → .WithOptional()  // 🚫 خطرناک!
   ```

2. ❌ **Nullable کردن FK بدون دلیل مشخص**
   ```sql
   -- ممنوع بدون بررسی داده‌های موجود:
   ALTER TABLE ... ALTER COLUMN ... NULL  // 🚫 خطرناک!
   ```

3. ❌ **تغییر منطق Authentication/Authorization**
   ```csharp
   // ممنوع بدون درک کامل:
   User.IsInRole(...) // تغییر منطق چک نقش
   GetCurrentPatientIdAsync() // تغییر منطق شناسایی بیمار
   ```

4. ❌ **تغییر محاسبات مالی**
   ```csharp
   // ممنوع بدون تست کامل:
   TotalPrice = ... // هر محاسبه‌ای مرتبط با پول
   ```

5. ❌ **Bulk Update/Delete روی جداول حیاتی**
   ```sql
   -- ممنوع بدون Backup:
   UPDATE Patients SET ... // 🚫 خطرناک!
   DELETE FROM AspNetUsers ... // 🚫 خطرناک!
   ```

## ✅ فرآیند صحیح تغییر (Correct Change Process)

### **گام‌به‌گام برای تغییرات حیاتی:**

```
1️⃣ STOP & THINK
   ├─ آیا واقعاً این تغییر لازم است؟
   ├─ آیا منطق فعلی را درک کرده‌ام؟
   └─ آیا راه‌حل بهتری وجود دارد؟

2️⃣ ASK USER
   ├─ مشکل دقیقاً چیست؟ (نمونه بخواه)
   ├─ رفتار مورد انتظار چیست؟
   ├─ چه سناریوهایی باید تست شوند؟
   └─ آیا محدودیت خاصی وجود دارد؟

3️⃣ ANALYZE IMPACT
   ├─ grep/codebase_search برای یافتن استفاده‌ها
   ├─ بررسی Database Dependencies
   ├─ چک کردن تست‌های موجود
   └─ لیست ماژول‌های تحت تأثیر

4️⃣ PROPOSE SOLUTION
   ├─ توضیح کامل تغییرات پیشنهادی
   ├─ لیست فایل‌هایی که تغییر می‌کنند
   ├─ توضیح تأثیرات جانبی
   └─ منتظر تأیید کاربر بمان

5️⃣ IMPLEMENT (بعد از تأیید)
   ├─ تغییرات تدریجی
   ├─ تست بعد از هر مرحله
   └─ لاگ تمام تغییرات

6️⃣ VERIFY
   ├─ بررسی Linter Errors
   ├─ بررسی Build Success
   ├─ تست سناریوهای اصلی
   └─ گزارش به کاربر
```

## 📖 مثال‌های واقعی (Real Examples)

### ❌ **اشتباه واقعی (گذشته):**

```
مشکل گزارش شده:
"CreatePatientAsync همیشه User ایجاد می‌کند - اشتباه است"

❌ تحلیل اشتباه AI:
- بدون پرسیدن سوال → فرض: "باید دو حالت داشته باشد"
- تغییر WithRequired → WithOptional (شکستن رابطه)
- ایجاد Migration برای Nullable کردن FK
- تغییر منطق CreatePatientAsync

✅ تحلیل صحیح:
- سوال: "چرا ایجاد User اشتباه است؟"
- سوال: "چه سناریویی باید بدون User باشد؟"
- بررسی منطق فعلی قبل از تغییر
- کشف اینکه منطق فعلی درست است!
```

### ✅ **رویکرد صحیح:**

```
گام 1: سوال از کاربر
"می‌توانید توضیح دهید چرا ایجاد User برای بیمار اشتباه است؟
آیا سناریوی خاصی وجود دارد که بیمار نباید User داشته باشد؟
مثلاً: پذیرش تلفنی، بیمار موقت، و غیره؟"

گام 2: درک منطق
"در حال حاضر منطق این است:
- منشی بیمار را پذیرش می‌کند
- سیستم Patient + User ایجاد می‌کند
- پیامک با credentials ارسال می‌شود
- بیمار می‌تواند لاگین کند
آیا این منطق اشتباه است؟"

گام 3: منتظر تأیید
(بعد از این سوالات، متوجه شدیم منطق فعلی درست است!)
```

## 🎯 چک‌لیست سریع (Quick Checklist)

قبل از هر تغییر روی ماژول حیاتی:

```
□ آیا منطق فعلی را کاملاً درک کرده‌ام?
□ آیا از کاربر سوال پرسیده‌ام?
□ آیا نمونه واقعی از مشکل دیده‌ام?
□ آیا تأثیرات جانبی را بررسی کرده‌ام?
□ آیا راه‌حل را با کاربر تأیید کرده‌ام?
□ آیا تغییرات قابل Rollback هستند?
□ آیا تست‌های لازم را شناسایی کرده‌ام?
```

**اگر جواب هر کدام "خیر" است → STOP!**
